# unit-test-spec-review

記入済みの **単体テスト仕様書／報告書**（データ移行の単体テスト結果）を1ファイル単位でレビューし、
指摘を出す。対象は「テストが実施され、判定まで記入された報告書」であって、設計書でもテスト仕様書の
ひな形でもない。

Validated on: `単体テスト仕様_V1.23.0_TXJAM066_001_入力項目選択肢名称ﾏｽﾀ.xlsx` ほか同フォルダ40ファイル。
件数・判定の突合ルールは**40ファイル全件に対して機械的に実行して校正済み**で、40件すべてが
規則どおりであることを確認した。

**このスキルは「指摘を減らす」方向に2度改訂されている。** 初版は判定「-」の未実施理由が無いこと、
および性能・ﾘｿｰｽ測定の実測値が無いことを重指摘として出したが、いずれも**運用上そう書くのが正しい**
箇所で、レビュー対象者から誤指摘と指摘された。後述の「指摘しないもの」を必ず先に読むこと。
新しい観点を足すときも、まず40ファイル一括照合で「全件がそうなっている＝運用」かどうかを
確かめてから指摘化する。規則を変えるときは同じバッチ検証をやり直すこと（後述のスクリプト）。

## 他スキルとの境界（最初に確認すること）

| 依頼 | 使うスキル |
|---|---|
| 記入済みの単体テスト仕様書をREVしたい | **このスキル** |
| 設計書（機能定義書/画面設計書/更新条件表/帳票設計書）をREVしたい | `rev-program-review`（rev-skills プラグイン） |
| 設計書から総合テスト仕様書(.xlsm)を作りたい | `integration-test-spec-generate`（test-spec-skills プラグイン） |

3つは**別プラグイン**として分けてある。設計書REVの8チェックはこのワークブックの構造を一切知らない
ので、単体テスト仕様書を `rev-program-review` に流してはいけない（`Ⅲ．入出力定義` も `更新条件表` も
存在しないシートを探して空振りする）。逆にこのスキルを設計書に向けてもいけない。
ファイル名が `単体テスト仕様_` で始まり、シートが `改訂履歴` と `ﾃｽﾄ仕様` の2枚だけなら、このスキルの対象。

## 読み方 — Excel COM ではなく openpyxl を使う

このワークブックは小さい（`ﾃｽﾄ仕様` は 57行×30列程度、`改訂履歴` は全社テンプレートの改訂履歴）。
`_shared/xlsx-excel-com-dump.md` の Excel COM ダンプは設計書のような大型ブック向けで、ここでは
**openpyxl のほうが速くて正確**。理由は2つある。

- **日付がそのまま読める。** COM ダンプは `Value2` を取るので `テスト実施日` が `46262` という
  シリアル値になり、毎回 1899-12-30 起点で手計算するはめになる。openpyxl は
  `datetime.datetime(2026, 8, 28)` を返す。
- **同一フォルダの全ファイルを1パスで横串比較できる。** 「この値はこのファイル固有の誤りか、
  全ファイル共通のテンプレート由来か」を切り分けるのに必須（後述の「全ファイル共通の事象」参照）。
  40ファイルの `ﾃｽﾄ仕様` を読むのに数秒しかかからない。

```python
import openpyxl, warnings
warnings.filterwarnings('ignore')   # wmf 画像の UserWarning が出るが無害
wb = openpyxl.load_workbook(path, data_only=True)   # data_only 必須（数式ではなく値がほしい）
ws = wb['ﾃｽﾄ仕様']
```

取り消し線による削除行がありうるので、疑わしい行は `data_only=False` で開き直して
`ws.cell(r, c).font.strike` を見る。シートが小さいのでセル単位で見ても安い。

`改訂履歴` シートは **全社テンプレート L0105 の改訂履歴**（Ver.1.0.3〜1.23.0、KCCS の是正対応履歴）で、
プログラム固有の記述は入らない。**読まなくてよい／指摘対象外**。実質のレビュー対象は `ﾃｽﾄ仕様` 1枚だけ。

## `ﾃｽﾄ仕様` シートのセルマップ（検証済み）

| セル | 内容 |
|---|---|
| `A1` | 文書種別（`AC1:AC5` のリストから選択） |
| `E3` / `N3` / `Q3` | 計画書Ｎｏ．／テスト実施日 自〜至 |
| `E4` / `E5` | システム名，件名／プログラム名，マクロ名（`移行ﾏｯﾋﾟﾝｸﾞ表(<TableID>_<枝番>_<名称>)`） |
| `A6:A9` / `G6:G9` | ﾚｽﾎﾟﾝｽ／排他／ﾒﾓﾘﾘｰｸ／ﾎｽﾄ連携 の各テストと**不要理由** |
| `AA6:AA9` / `AB6:AB9` | 同４行の **要=`AA` / 不要=`AB`**（bool。`AA=True` なら「要」） |
| `E10` / `N10` | **テスト件数** / **障害件数** |
| `E11` + `A12:A14` | テスト環境（DBｻｰﾊﾞｰ2件、クライアントOS/CPU/メモリ） |
| `A17:A32` / `G17:G32` / `I17:I32` | 総合ﾃｽﾄ項目 S1〜S16 の 要／不要 と **未実施理由** |
| `A33` / `B33` / `O33` / `Q33` | 明細ヘッダ（Ｎｏ．／テスト項目／担当／**担当**〈再テスト側〉） |
| `A34〜` / `B` | 明細：Ｎｏ．／テスト項目 |
| `O` / `P` | **初回**の担当／判定 |
| `Q` / `R` | **再テスト（是正後）** の担当／判定 |
| `S` | 備考・是正内容（自由記述） |

**`Q`/`R`/`S` は余白ではなく再テスト欄。** NG が出た行だけ埋まる。実例：`TXJCM202_001` は
`P45=NG` → `Q45=日高` `R45=OK`、`S45` に是正内容（課題管理No19、ｿｰﾄ条件に OBJECT_ID/SERVER_ID を追加）。
NG が1件も無いファイルでは `Q`/`R` は全行 `-` になるので、初見だと空列に見える。見落とすと
「NGなのに再テスト結果が無い」「障害件数が合わない」を誤指摘する。

明細の行種別は `A` 列のＮｏ．のハイフン数で判別する。

- `S1`（0個）= 大区分見出し
- `S1-1`（1個）= 中区分。`P` 列には**判定ではなく実施日**が入る（`R` 列は再テストの実施日）。
  実施日は `datetime` のことも `'7/16'` という文字列のこともあるので両方受ける
- `S1-1-1`（2個）= **リーフ項目**。`P` 列が判定。件数集計はこの行だけを数える

判定値は **`OK` / `NG` / `-` / `不可` の4種類**（40ファイルの全リーフ項目を走査して確認）。
`不可` は入力規則のリスト（`AD1:AD3` の `OK`/`NG`/`NG→OK`）に無い手入力値で、「実施不可」の意。
**`-` と `不可` はどちらも「判定なし」として件数から除く**。`不可` を `NG` と誤読すると障害件数が
合わなくなるので注意する。

`AA1`〜`AD5` は入力規則用のリスト定義域（文書種別リストと `OK`/`NG`/`NG→OK`）。指摘対象ではない。

## 定型の項目構成

移行方式によって明細の形が違う。どちらかに当てはまらなければ、まず構成そのものを疑う。

**SQL移行（`移行ﾏｯﾋﾟﾝｸﾞ表`、リーフ16項目）**
`S1-1` カラム毎確認（-1 固定値／-2 NULL／-3 通常パターン／-4 境界値／-5 改行／-6 備考／-7 最大文字数、最大値）、
`S1-2` テーブル/結合条件毎確認（-1 結合条件の一致／-2 絞込条件の確認／-3 移行件数が想定件数か）、
`S1-3` エラー処理確認（-1／-2）、`S5-1` 性能（-1 正常終了・コミット／-2 時間を測定する）、
`S6-1` ﾘｿｰｽ測定（-1 メモリ量／-2 TMP領域80%）。

**手動移行（ファイル名に `手動移行_`、リーフ4項目）**
`S1-1` カラム確認（-1 固定値／-2 備考内容の確認）、`S1-2` 挿入SQL確認（-1 DB登録／-2 移行件数）。
S5/S6 は「不要」となり、`S5`/`S6` の明細ブロック自体が存在しない。

## 指摘しないもの（運用として確認済み — 誤指摘の常連）

このワークブックは「空欄に見えるが、運用上そこに書かないのが正しい」箇所が多い。次の2つは
**確認済みで指摘対象外**。どちらも初版のこのスキルが実際に誤指摘したもので、レビュー前に必ず
読んでおくこと。

### 判定「-」＝テスト対象なし。理由の記載も不要

`S1`／`S5`／`S6` のリーフ項目に付く「-」は、**そのテーブルにテスト対象が存在しない**ことを表す
（該当カラムが無い／結合条件が無い／測定対象が無い）。理由を書く必要も無い。
`S1-1-5 改行`、`S1-1-6 備考`、`S1-2-1 結合条件の一致`、`S6-1-2 TMP領域80%` はいずれもこれに当たる。
**「未実施理由が無い」という指摘を出してはいけない。** 単一テーブルのマスタ移行なら結合条件が
そもそも無いので `S1-2-1` が「-」なのは正常であり、これを「移行SQLの妥当性を誰も確認していない」と
書くのは誤指摘になる。

唯一の例外：横串スクリプトで**同じ項目が他ファイルでは軒並み `OK` なのにこのファイルだけ「-」**という
並びが見えたときだけ、「本当に対象なしか」を一言確認してよい。それ以外で「-」に言及しないこと。

### 実測値（想定件数・測定時間・メモリ量）は別紙管理。本書に書かない

`S1-2-3`（移行件数が想定件数になっているか）、`S5-1-2`（時間を測定する）、
`S6-1-1`（メモリ量が大幅に増えないこと）が `OK` なのに数値が残っていないのは**正常**。
**実測値は別紙で管理している**ため、このワークブックに書く必要は無く、
**「別紙に記載」という参照の記載すら不要**。

`AC6` の注記「テスト時は下記テスト環境及び想定件数、目標値、実績値等を明記すること」は
全社テンプレートの定型文で、40ファイル全件に同じ文言が入っている。**この注記を根拠に
「実績値が未記載」と指摘してはいけない。** 「エビデンス性が無い」という論法も同様に使わない。

## チェック項目

### 1. 判定「不可」（実施不可）の理由が書かれていない

指摘対象は **`P` 列が `不可` の項目だけ**。`不可` は入力規則リストに無い手入力値で「テスト対象は
あるが実施できなかった」の意であり、「-」（対象なし）とは意味が違う。理由が `S` 列（備考欄）にも
`I17:I32` にも無ければ指摘する。実例：`TXJAM061_002` は `S1-3-1`/`S1-3-2`（エラー処理確認）が
`不可` で、理由がどこにも書かれていない。40ファイル中この1ファイル2件だけが該当する。

`I17:I32`（S1〜S16の未実施理由欄）は**大区分単位**なので、リーフ項目個別の理由はそこには書けない。
書ける場所は **`S` 列の備考欄**で、`TXJCM202_001` の `S45` に是正内容が書かれている実績がある。

### 2. テスト件数・障害件数の整合

40ファイル全件で検証した運用ルール：

- **`E10` テスト件数 = `P` 列に判定が記入されたリーフ項目数（`-` と `不可` を除く）**。項目総数ではない。
  例：`TXJAM060_001` は 16項目・`-`1件 → 件数15。`TXJAM066_001` は 16項目・`-`4件 → 件数12。
- **`N10` 障害件数 = 「`P=NG` の件数 → そのうち `R` で `OK` にならなかった件数」**。
  NG が無ければ `0`。ただし **`0→0` と書くファイルもあり（3件確認）、これは表記揺れであって誤りではない**。

**「件数＝項目数と違う」だけでは指摘にしない** — 上のルールでは一致しないのが正常。
ルールから外れたときだけ指摘する。40ファイルを一括照合した結果、**ずれているファイルは1件も無かった**ので、
ずれが出たら「まず自分の数え方（`不可` の扱い、リーフ行の判定）を疑う」こと。

次のスクリプトで全ファイルを一括照合できる。1ファイルのREVでも、これを回してから
「このファイルだけの誤りか」を確定させるのが速い。

```python
import glob, openpyxl, warnings
warnings.filterwarnings('ignore')
for f in sorted(glob.glob('*.xlsx')):
    ws = openpyxl.load_workbook(f, data_only=True)['ﾃｽﾄ仕様']
    leaves = [r for r in range(34, ws.max_row + 1)
              if ws.cell(r, 1).value and str(ws.cell(r, 1).value).count('-') == 2]
    judged = [r for r in leaves if ws.cell(r, 16).value not in (None, '', '-', '不可')]
    ng     = [r for r in leaves if ws.cell(r, 16).value == 'NG']
    fixed  = [r for r in ng if ws.cell(r, 18).value == 'OK']
    exp    = 0 if not ng else f"{len(ng)}→{len(ng) - len(fixed)}"
    if ws['E10'].value != len(judged) or str(ws['N10'].value) not in (str(exp), '0→0'):
        print('MISMATCH', f, ws['E10'].value, len(judged), ws['N10'].value, exp)
```

### 3. 要／不要フラグと理由欄の整合（`A6:A9`）

`AA`（要）/`AB`（不要）の bool と `G` 列の不要理由を突き合わせる。

- 「不要」なのに理由が空 → 指摘（重）
- 「要」なのに理由欄に文章が入っている → 記入誤りの疑い
- 「要」の行の理由欄が空白なのは**SQL移行ファイルでは常態**（`G8` ﾒﾓﾘﾘｰｸが典型で、`-` を書いて
  いるのは `TXJAM070_001` だけ、手動移行ファイルは全件「手動移行のため」と書く）。
  単独では指摘にせず、他に体裁指摘を出すときに添える程度にとどめる

同様に `A17:A32` の S1〜S16 も、「不要」なら `I` 列に理由が必要。

### 4. テスト項目本文の誤記

`B` 列のテキストを読む。テンプレート由来の既知の誤記が1件ある。

- `S1-3-1`：「エラー発生時に後続処理が行われること**エラーが発生しても**トランザクションが
  コミットされること**)**」— 開き括弧が欠落しており、2文が繋がって読めない。
  正：「…行われること**(**エラーが発生しても…されること)」。
  **大半のファイルに共通**（実測40件中28件）なので、複数ファイルをまとめてREVするときは1件に集約する。

### 5. 文書種別と体裁（軽指摘）

- `A1` が `総合テスト仕様書／報告書` なのに、ファイル名は `単体テスト仕様_`。
  **確認済みで40ファイル全件がそうなっている**ため、個別ミスではなく総合テンプレート流用の運用と
  思われる。毎回の個別指摘にはせず、「運用として意図的か確認」の1件として出す。
- 未実施理由欄の `－`（全角・先頭スペース付き）と判定欄の `-`（半角）の混在。テンプレート由来。
- S2〜S14 の未実施理由が一律「実施対象外のため」なのに、`G7` の排他テストだけ
  「移行時、他で更新されることがない為」と具体的 → 粒度を揃える提案（軽）。

### 6. 日付・担当の整合

- `N3`〜`Q3` のテスト実施日の範囲に、各中区分行（`S1-1` など）の `P` 列の実施日が収まっているか。
  1日で終わっていれば `N3 = Q3`（`TXJAM066_001`）、複数日に跨れば範囲になる（`TXJCM202_001` は
  7/16〜7/22 で、中区分の実施日 7/16・7/21・7/22 と整合）。範囲外の実施日があれば指摘。
- 担当 `O` 列が全リーフ項目に入っているか（`TXJAM061_002` の `S1-2-1` は判定OKなのに担当が `-` ＝記入漏れ）。
  NG があった行は `Q` 列（再テスト担当）と `R` 列（再テスト判定）が埋まっているか。

### 7. 検証できない範囲を明示する

このワークブックだけでは、**移行マッピング表（`TXJAM066_001` 等）そのものとの突合はできない**。
- `S1-1`「カラム毎確認」が実際の移行カラムを網羅しているか
- `S1-2-1` の結合条件がマッピング表と一致するか

はレビュー範囲外である旨をレポート末尾に明記し、マッピング表の場所を聞く。黙って省略しない。

## 全ファイル共通の事象と個別の誤りを切り分ける

同一フォルダに数十ファイルある。**指摘を出す前に、その事象が対象ファイル固有かを横串で確認する。**
共通なら「テンプレート／運用起因」として1件にまとめ、固有なら個別指摘として重く扱う。

```python
import glob, openpyxl, warnings
warnings.filterwarnings('ignore')
for f in sorted(glob.glob('*.xlsx')):
    ws = openpyxl.load_workbook(f, data_only=True)['ﾃｽﾄ仕様']
    print(f[:55], ws['A1'].value, ws['E10'].value, ws['N10'].value)
```

確認済みで全件共通のもの：`A1` の文書種別、`E3` の計画書Ｎｏ．`MB2206-D005-12`、
`AC*` の注記文、`改訂履歴` シートの内容。

## フォルダ一括REV → 指摘一覧Excelの出力

「配下の単体テスト仕様書を全部REVして、指摘を1つのExcelにまとめて」と頼まれたときは、
`scripts/build_rev_report.py` を対象フォルダに向けて実行する。チェック1〜7を40ファイル規模に
そのまま適用し、`REV指摘一覧_単体テスト仕様_<バージョン>.xlsx` を同フォルダに出力する。
`SRC` / `OUT` の2定数を書き換えるだけで別フォルダに使える。スクリプトは指摘の判定ロジックを
そのまま持っているので、**チェック観点を追加・修正したらこのスクリプトも同時に直すこと**
（SKILL.md 本文とスクリプトが食い違うと、対話REVと一括REVで結果が変わる）。

出力は2シート。

- **`指摘一覧`** — 1指摘1行。列は `No. / ファイル名 / テーブルID / 移行方式 / 区分 / 重要度 /
  チェック観点 / セル / 指摘内容 / 根拠・確認事項`。ヘッダ行にオートフィルタ、`C2` でウィンドウ枠固定、
  重要度はセル色（重=赤／中=黄／軽=緑）。
- **`ファイル別サマリ`** — 1ファイル1行。項目数・判定済・NG・テスト件数・障害件数・実施日と、
  重／中／軽の指摘件数。

### 「区分」列でテンプレート共通の指摘を畳む

40ファイル一括だと、**テンプレート由来の指摘が件数の大半を占める**（実測：112件中68件が共通）。
共通分をレポートから落とすと「このファイルは見たのか」が分からなくなり、全件並べると個別の
不具合が埋もれる。そこで**落とさずに `区分` 列（`個別` / `共通`）で仕分ける**。
並び順も `個別` を先頭に固定し、共通は後ろにまとめる。読む側は `区分 = 個別` で
フィルタすれば実質的な指摘だけを見られる。

今わかっている共通指摘：`A1` の文書種別（40件）、`S1-3-1` の括弧欠落（28件）。

### 一括REVでしか出ない観点

1ファイル単体では判断できず、横串で初めて指摘になるものがある。スクリプトはこれを実装済み。

- **テスト項目文言の表記揺れ** — 同じNo.なのに文言が違う。実測で `S5-1-1` が3種類
  （「正常終了すること」20／「コミットできることを確認する」6／「正常にSQLが終了すること」2）、
  `S1-1-6` が2種類（「備考」25／「備考内容の確認」3）。多数派を基準に少数派を軽指摘にする。
- **テスト環境記載の不一致** — `A14` のOS記載が29件は Windows Server 2022／96GB、11件は
  クライアントPC（Windows 11 Pro／メモリ8GB）。**S5 性能／S6 ﾘｿｰｽ測定が「要」なのに
  クライアントPC記載**のファイルだけを指摘にする（実測11件）。測定値そのものは別紙管理なので
  問われるのは「どの環境で測ったか」だけ。
- **接続先DBサーバ名の表記揺れ** — `SJX／MPASC1`（22件）と `SJX_T1／MPASC1_T1`（18件）。
  IPとSIDは同一なので、別環境なのか表記揺れなのかの確認事項として軽指摘。

## レポートの形

1ファイル1レポート。重要度（重／中／軽）順に並べ、各指摘に**セル座標**を添える（`[48,2]` ではなく
`B48` のような列記号表記のほうが利用者が追いやすい）。最後に「指摘なしだった確認項目」と
「このファイルだけでは検証できない範囲」を必ず書く — 何を見て何を見ていないかが分からない
レポートにしない。
